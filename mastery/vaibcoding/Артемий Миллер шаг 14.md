# Артемий Миллер шаг 14: Цикл проверки после фичи

## Зачем

После фазы AI часто защищает свой код. Миллер заставляет его смотреть заново: ошибки, упущения, реальность проблемы, свежий взгляд, security review. Это фильтр против галлюцинаций, лишних исправлений и "кода ради кода".

## Ход 1: найти ошибки

```text
Прочитай последние изменения свежим взглядом.

Найди ошибки по категориям:
- off-by-one
- null / undefined
- edge cases
- race conditions
- утечки данных
- нарушения инвариантов из architecture/03-данные/правила-нерушимые.md
- несоответствие AGENTS.md

Если ошибок не видишь, назови 3 места, где это сломается при росте нагрузки в 100 раз.
Не исправляй. Только список.
```

Потом:

```text
Докажи каждый пункт.

По каждому:
- это реальная ошибка или паранойя?
- какой сценарий воспроизводит проблему?
- какой файл/строка/условие это подтверждает?

Не исправляй, пока не отделишь реальные ошибки от шума.
```

Потом:

```text
По реальным ошибкам выбери лучшее решение и примени.

Не давай варианты. Дай решение.
После правки покажи diff и объясни, почему это не ломает соседнюю логику.
```

## Ход 2: что упустили

```text
Что мы упустили в этой фазе?

Проверь:
- сценарии, которые не учли
- пограничные случаи
- зависимости от других частей проекта
- что будет через месяц использования
- что будет, если пользователь сделает не то, что мы ожидаем

Список без исправлений.
```

Потом:

```text
Докажи по каждому пункту:
- это реальное упущение в нашем проекте
- или теоретический риск, который можно отложить

Учитывай:
- цель первой фазы
- аудиторию
- текущие объёмы
- приоритет: запустить -> продать -> масштабировать
```

## Ход 3: это реально проблема?

```text
По каждому найденному пункту докажи, что это РЕАЛЬНО проблема В НАШЕМ проекте.

Учитывай:
- продукт из AGENTS.md
- architecture/
- business/, если есть
- объёмы на старте
- критерий готовности фазы

Если "теоретически может, но не критично" - вычеркни.
Если реально критично - исправь.
```

## Ход 4: свежий взгляд после правок

```text
После правок посмотри свежим взглядом.

Проверь:
- что появилось нового
- что могли сломать
- какие регрессии возможны
- не добавили ли мы лишнюю сложность

Только новое. Не повторяй старые пункты.
```

## Ход 5: security review

```text
Security review последних изменений.

Проверь:
- опасная тройка: личные данные + чужой контент + отправка наружу
- SQL/NoSQL injection
- XSS / CSRF / SSRF
- утечки токенов в логи
- .env в коде или коммитах
- права на API
- rate limiting
- валидация входов
- подробные ошибки наружу
- платежи и idempotency, если есть оплаты

По каждому пункту:
- OK
- починить: что именно
- не применимо: почему

Только воспроизводимое. Не "можно было бы".
```

## Усиленный Codex-ритуал

Перед важным коммитом:

```text
Свежий взгляд, без защиты предыдущего решения.

Возьми последние изменения проекта и пройдись по чек-листу безопасности:
1. Ввод от пользователя валидируется?
2. Секреты не утекли?
3. Админка закрыта авторизацией?
4. Личные данные не падают в логи?
5. Ошибки наружу без stack trace?
6. Платёжные формы защищены от двойной оплаты?
7. API-ключи не попали во фронтенд?
8. Загрузка файлов безопасна?

Для каждого пункта дай: запрос/сценарий -> результат -> вывод.
```

## Готовность

Шаг готов, когда после проверки остались только осознанно отложенные риски, а реальные ошибки исправлены.
