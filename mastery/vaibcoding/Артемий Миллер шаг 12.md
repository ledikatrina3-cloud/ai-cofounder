# Артемий Миллер шаг 12: План первой фичи и критика

## Зачем

План - это буфер между архитектурой и кодом. У Миллера большая фича не запускается напрямую: сначала план в файл, потом проверка "как было / как будет", затем жесткая критика и только потом реализация.

## Промпт 1: план первой фичи

```text
Прочитай:
- AGENTS.md
- architecture/
- memory/MEMORY.md, если есть
- business/INDEX.md, если есть

Напиши план первой фичи: <одно предложение фичи>.

Файл: plans/YYYY-MM-DD-<короткое-имя>.md

Формат:

# План: <название>

## Контекст
Что уже известно из architecture/ и business/.

## Критерий: фича готова
Один проверяемый результат.

## Фазы
3-7 фаз. Каждая фаза 1-3 часа работы Codex.

Для каждой фазы:
### Фаза N: <название>
- Статус: [ ]
- Цель
- Deliverable
- Критерий "сделано"
- Задачи [ ]
- Что НЕ делать

## Риски

## Итог
Пока пустой. Заполнить после реализации.

Важно:
- думай не в человеко-часах, а в своих циклах работы
- не начинай реализацию
- если архитектура неполная, остановись и скажи, какой файл дополнить
```

## Промпт 2: проверка "как было / как будет"

```text
Прочитай plans/YYYY-MM-DD-<имя>.md.

Объясни простыми словами, без технических терминов:
- как было ДО фичи: 1 абзац
- как станет ПОСЛЕ фичи: 1 абзац
- что конкретно пользователь или владелец сможет сделать, чего раньше не мог
- что НЕ изменится

Не правь план. Только объясни.
```

Если объяснение не совпадает с твоей реальной идеей:

```text
Моя реальная супер-идея:
<вставь расшифровку голосом или текст>

Пересобери план так, чтобы он вел именно к этой идее.
Сначала покажи новое "как было / как будет".
Файл плана не трогай до моего "ок".
```

## Промпт 3: жесткая критика плана

Запускай в отдельном Codex-треде или после явного запроса "свежий взгляд".

```text
Прочитай plans/YYYY-MM-DD-<имя>.md.

Ты сеньор с 15 годами опыта в домене. Жёстко проверь план:
- лишние или избыточные фазы
- упущенные фазы
- расплывчатые критерии "сделано"
- риски, которые не учли
- "код для кода" без пользы
- конфликты с architecture/
- нарушения AGENTS.md

Не предлагай переписанную версию.
Дай список замечаний с обоснованием:
| Замечание | Почему важно | Файл/фаза | Критичность |
```

## Промпт 4: применить критику

```text
Вот замечания к плану:
<вставить замечания>

По каждому замечанию реши:
- код для кода
- теоретический риск
- реальная польза для нашего проекта

Реальную пользу докажи ссылкой на architecture/, business/ или критерий фичи.
Примени только доказанные правки.
Покажи итоговый список изменений в плане.
```

## Готовность

Переходи дальше, когда план выдержал критику, каждая фаза имеет deliverable, а "как будет" звучит как реальная польза.
