# Артемий Миллер шаг 8: Архитектурное ядро

## Зачем

Здесь решается, как продукт думает: главный кирпич, память, триггеры, способности, права и данные. Это слой, который потом тяжело переделывать.

## Промпт 1: главный кирпич

```text
Прочитай:
- idea/
- architecture/01-обзор/
- architecture/02-ядро/характер.md

Сначала составь список всех типов сущностей из idea/.
Потом проверь гипотезу: можно ли свести их к 1-2 базовым кирпичам.

Образец:
- Notion свёл всё к "блоку".
- Linear - к "задаче".
- Stripe - к объекту с типизированным id.

Заполни architecture/03-данные/главный-кирпич.md:

# Главный кирпич

## Гипотеза
Описание кирпича: id, тип, свойства, родитель, дети.

## Список вариантов
Какие бывшие отдельные сущности становятся кирпичом с типом.

## Что я выигрываю
3 фичи, которые теперь работают для всех типов: поиск, история, права, экспорт, аудит.

## Что я проигрываю
Где кирпич неудобен и почему я готова на это пойти.

ВАЖНО: если один кирпич ломает половину сценариев, не натягивай. Покажи оба варианта и спроси, что выбрать.
```

## Промпт 2: 4 слоя памяти

```text
Прочитай:
- architecture/01-обзор/
- architecture/02-ядро/характер.md
- architecture/03-данные/главный-кирпич.md

Заполни architecture/02-ядро/память-и-состояние.md по 4-слойной модели:

# Где живёт память

## Слой 1. Сейчас
- Что попадает в текущий запрос
- Лимит размера
- Что выкидывается первым

## Слой 2. Недавнее
- Где хранится
- Срок жизни
- Когда переезжает в слой 3

## Слой 3. Постоянное
- Где хранится
- Кто пишет
- Кто читает

## Слой 4. Навыки
- Где хранится
- Как обновляется

## Когда недавнее переезжает в постоянное
Например: раз в неделю агент читает события за 7 дней, извлекает повторяющиеся факты, удаляет старое.

## Когда постоянное очищается
Например: если факт не подтверждался 90 дней, помечается "устарел".

Правило: для маленьких проектов текстовые файлы + git лучше векторных баз. Векторную базу обсуждать только если фактов больше 10 000.
```

## Промпт 3: триггеры

```text
Прочитай:
- architecture/02-ядро/характер.md
- architecture/02-ядро/память-и-состояние.md

Заполни architecture/04-потоки/триггеры.md.

Сделай таблицу:
| Триггер | Тип | Что делает | Лимит времени | Защита от дублей | Если упал |

Типы триггеров:
- действие пользователя
- внешнее событие
- расписание
- изменение файла
- внутреннее событие
- фоновая задача

Для каждого триггера укажи:
- лимит времени
- защиту от дублей
- что делать при сбое

Если есть AI-агент, добавь раздел:

## Ночной режим
- что агент делает в 03:00
- какие события читает
- какие факты переносит в постоянную память
- как чистит дубли
- какой лимит токенов или времени
```

## Промпт 4: способности и права

```text
Прочитай:
- architecture/01-обзор/
- architecture/02-ядро/характер.md
- architecture/04-потоки/триггеры.md

1. Создай в architecture/02-ядро/способности/ по одному файлу на способность.

Способность - одно действие, которое продукт умеет делать.
У AI-агента - каждый инструмент.
У обычного продукта - каждое API-действие.

Структура файла:
# Способность: <название>

## Когда применять
1-2 сценария.

## Когда НЕ применять
Граница с другими способностями.

## Примеры
2-3 правильных вызова.

## Что может пойти не так
Что делать при ошибке.

## Уровень доступа
гость / пользователь / премиум / админ / только система.

2. Заполни architecture/02-ядро/права-доступа.md:

| Действие | Гость | Пользователь | Премиум | Админ | AI-автоматика |

Ячейки:
- сам
- спросить
- эскалировать
- запретить

Правила:
- Обычное и обратимое - сам.
- Сообщения наружу и оплаты до лимита - спросить.
- Деньги выше лимита, удаления, юридические действия - эскалировать.
```

## Промпт 5: сущности и схема

```text
Прочитай:
- architecture/03-данные/главный-кирпич.md
- architecture/02-ядро/память-и-состояние.md
- architecture/02-ядро/права-доступа.md
- architecture/04-потоки/триггеры.md

Заполни три файла:

1. architecture/03-данные/сущности.md
Таблица:
| Сущность | Назначение | Ключевые поля | Связи | Индексы |

2. architecture/03-данные/схема-связей.md
Mermaid ER-диаграмма со всеми связями. Внешние ключи помечены явно.

3. architecture/03-данные/правила-нерушимые.md

# Правила, которые никогда не должны нарушаться

## Базовые
- Идентификатор всегда уникален.
- Связи всегда валидны.
- Дата создания не позже даты обновления.
- Удалённые записи не возвращаются в обычных запросах.

## Бизнес-правила
Добавь специфичные для проекта правила.

После этого сгенерируй architecture/03-данные/schema.prisma или аналог схемы под выбранный стек.

Правила:
1. Каждое поле имеет причину.
2. "Может пригодиться" - выкинь.
3. Каждая связь явная.
4. Индексы только на реальные горячие запросы.
```
