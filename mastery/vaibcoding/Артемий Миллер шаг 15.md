# Артемий Миллер шаг 15: Production-безопасность

## Зачем

После цикла проверки, но до commit/deploy, нужен отдельный слой безопасности. Вайбкодинг ускоряет сборку продукта, но на проде ты отвечаешь не скоростью, а секретами, данными, деньгами и восстановлением после ошибки. Поэтому безопасность не размазывается по всему процессу: у неё есть свой шаг перед фиксацией и выкладкой.

Главный принцип: сначала отфильтровать чек-лист под конкретный проект, потом закрыть минимум, потом средний уровень, потом максимальные меры.

## Промпт 0: отфильтровать чек-лист

```text
Проанализируй мой проект и отфильтруй security-чеклист под меня.

Прочитай:
- AGENTS.md
- architecture/
- package.json / pyproject.toml / другие файлы зависимостей
- .gitignore
- .env.example, если есть
- README или deploy-документацию

Для каждого пункта дай статус:
- ДЕЛАТЬ сейчас
- ОТЛОЖИТЬ
- ПРОПУСТИТЬ

Объясни почему.
В конце дай ТОП-3 security-действия на сегодня.
Ничего не исправляй без моего "ок".
```

## Минимум перед коммитом

### 1. Секреты и gitleaks

```text
Поставь gitleaks/pre-commit или эквивалентный механизм проверки секретов, который подходит этому проекту.

Сделай:
1. Определи стек и package manager.
2. Предложи самый простой способ запуска проверки.
3. Добавь команду в README или AGENTS.md, если это принято в проекте.
4. Запусти проверку.
5. Если найдены секреты, не показывай их полностью. Покажи файл, тип секрета и что делать.

Не коммить.
```

### 2. `.env` и история git

```text
Проверь, что .env и локальные секреты не попали в git.

Сделай:
1. Проверь .gitignore.
2. Проверь, есть ли .env.example без реальных секретов.
3. Проверь историю git на признаки секретов:
   - .env
   - sk-
   - DATABASE_URL
   - API_KEY
   - TOKEN
4. Если есть риск утечки, остановись и дай план ротации ключей.

Не печатай полные значения секретов.
```

### 3. Бэкап локальной работы

```text
Проверь, какие важные папки не попадают в git.

Особенно:
- local data
- uploads
- sqlite/db files
- generated assets
- notes, которые нужны для продукта
- raw research

Предложи простой backup-план:
1. Что бэкапить.
2. Куда.
3. Как часто.
4. Как проверить восстановление.

Ничего не удаляй и не перемещай без команды.
```

## Средний уровень перед деплоем

```text
Проверь production-готовность проекта.

Фокус:
1. Есть ли отдельные ENV для prod.
2. Есть ли readonly-роль для production DB, если проекту нужен доступ только на чтение.
3. Есть ли backup базы и файлов.
4. Проверялось ли восстановление из backup.
5. Закрыта ли админка.
6. Не уходят ли личные данные в логи.
7. Есть ли rollback-план.

Выдай таблицу:
Пункт | статус | что сделать | критичность

Исправляй только пункты, которые я явно выберу.
```

## Максимальный уровень

```text
Проверь максимальные меры безопасности для проекта, если он работает с деньгами, личными данными, подрядчиками или боевыми API.

Оцени:
- отдельный профиль браузера для рабочих аккаунтов
- отдельные ключи для разработки и прода
- минимальные права для подрядчиков
- запрет передачи боевых ключей в чаты
- аудит доступов
- журнал деплоев
- 9 признаков опасного изменения: секреты, деньги, права, база, миграции, персональные данные, внешняя отправка, удаление, массовая рассылка

Сделай не общий чек-лист, а список конкретных действий для этого проекта.
```

## Как это адаптировано под Codex

В Codex главным механизмом контроля являются `AGENTS.md`, sandbox/approval, явные команды пользователя, проверки перед финальным ответом и аккуратная работа с git. Не полагайся на несуществующие локальные настройки. Если проект поддерживает hooks/config для проверок, добавляй их в принятом формате проекта.

## Готовность

Шаг готов, когда секреты проверены, `.env` не в git, есть понятный backup-план, production ENV отделены от локальных, а опасные действия требуют явного подтверждения.
