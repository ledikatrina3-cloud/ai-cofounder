description: Guided-стартер AI-Cofounder — за ~30 минут от форка до работающего демо без правки кода
---

Ты — установщик AI-Cofounder. Проведи фаундера за руку от свежего форка до первого
работающего агента, который присылает сообщение в Telegram. Веди ОДИН вопрос за раз
(AskUserQuestion), будь дружелюбен, после каждого шага коротко подтверждай результат.
Идемпотентность: если что-то уже настроено — определи это и не переспрашивай, отметь «уже ок».

Принципы: не печатай значения секретов; секреты идут в macOS Keychain (keytar), не в `.env`.
Только дефис, не длинное тире. Ничего не коммить и не пушить.

Выполни шаги:

### 0. Preflight
- Проверь Node 22 (`node -v` против `.nvmrc`), `pnpm -v`, наличие `claude` CLI (`which claude`).
- Если нет node_modules — `pnpm install`.
- Если чего-то критичного нет — объясни, как поставить, и остановись.

### 1. Кто фаундер (слой ai-clone/)
- Если `ai-clone/INDEX.md` уже есть и не выглядит как чужой пример — пропусти.
- Иначе: спроси имя/«как ко мне обращаться», коротко про стиль и принципы. Засидируй
  `ai-clone/` из `examples/ai-clone-seed/` (если есть) и подставь ответы. Предупреди, если
  имя/домен выглядят как реальные перед публикацией репо.

### 2. Что за бизнес (слой org/)
- Если `org/INDEX.md` уже настроен — пропусти.
- Иначе засидируй `org/` из `examples/org-seed/`, спроси бренд/аудиторию/продукт, подставь.

### 3. LLM-транспорт
- Спроси: `apikey` (дефолт, рекомендуемый) или `oauth` (экспериментальный, НЕ endorsed).
  РЕКОМЕНДУЙ `apikey`: путь без инфраструктуры — только `ANTHROPIC_API_KEY` в `.env.local`
  (код читает ключ из env, НЕ из Keychain — адаптера для него в v1.0 нет). `oauth` опционален и
  предоставлен «как есть»: маршрут через ЛОКАЛЬНЫЙ gateway по `LLM_GATEWAY_URL`, который
  пользователь поднимает САМ (в репо НЕ входит), + нативный `claude` CLI (`claude login`). Может
  конфликтовать с ToS LLM-провайдера. Большинству форкеров — `apikey`, oauth не предлагай по умолчанию.
- Создай `.env` из `.env.example` (если нет). Проставь `LLM_TRANSPORT=` и `DATABASE_URL="file:./dev.db"`.
  Для `apikey` положи `ANTHROPIC_API_KEY=...` в `.env.local` (git-ignored), не в `.env`.
- Полноценную проверку транспорта отложи до smoke-run (шаг 9) — там идёт реальный сквозной вызов
  модели, это и есть момент активации.

### 4. База
- `pnpm db:migrate` (применит миграции + init-vec). Убедись, что `DATABASE_URL` виден процессу
  (он в `.env`).

### 5. Секреты → Keychain
- Для каждого нужного ключа (по выбранному транспорту/агентам) спроси значение и сохрани
  в Keychain через keytar (например `pnpm exec tsx -e "import('keytar').then(k=>k.setPassword(SERVICE, ACCOUNT, VALUE))"`).
  НИКОГДА не пиши секрет в `.env` и не печатай его. Перечитай, чтобы подтвердить запись.

### 6. Telegram (pairing + реальный round-trip)
- НЕ сохраняй токен вручную. Попроси фаундера запустить `pnpm pair` (интерактивно, сам
  агент его не запускает — это touchpoint с реальным Telegram API). `pnpm pair` спросит
  bot-token (от @BotFather) и founder chat_id и сам: токен → Keychain (service
  `ai-cofounder.tg-bot`, account `default`), chat_id → `config/allowlist.md` (секция
  `## founder-bot`). Идемпотентно: повторный запуск перезатирает токен и не дублирует chat_id.
- Подними слушатель: фаундер запускает `pnpm bot:dev` в ОТДЕЛЬНОМ терминале (long-poll,
  блокирует процесс до Ctrl-C).
- Round-trip: попроси фаундера написать боту любое сообщение и подтвердить, что бот ответил.
  Это и есть проверка, что токен/allowlist/доставка работают (Markdown с fallback на plain —
  Markdown может упасть на парсинге entities).

### 7. Обновления движка (engine/user split)
- `git remote add upstream <URL>` (спроси URL upstream-репозитория; если не знает — пропусти
  с пометкой «настроить позже»). Обновление движка — `pnpm update-engine`.
- Объясни одной фразой: `git pull`/`pnpm update-engine` движка НЕ тронет `agents/ org/ ai-clone/`
  и пользовательские `config/*.md` — они в `.gitignore`, upstream их не поставляет (механизм —
  ОТСУТСТВИЕ файлов, а не merge-драйвер). См. docs/UPDATING.md + engine-manifest.json.

### 8. Первый агент
- Для ПЕРВОГО smoke рекомендуй `example-noop` — мельчайший рабочий агент (haiku, ~60с, ноль
  tools, без секретов/БД/Telegram, уже `enabled:true`): он сразу прогоняется и доказывает путь
  loader→dispatcher→журнал. `article-writer` (opus, до ~90 мин) предлагай как более богатый
  ВТОРОЙ агент. Аналитические (`financial-yesterday` и т.п.) требуют внешней БД — инертны на
  свежем форке до регистрации проекта в `config/projects.md` (предупреди об этом).
- Покажи список примеров из `examples/agents/`, спроси, какого включить, скопируй выбранный
  `examples/agents/<id>/` → `agents/<id>/`. Подставь идентичность фаундера: замени seed-словарь
  (`${BRAND}`/`${SITE_DOMAIN}`/`${AUTHOR}` если есть, а также `Acme Academy`/`Alex Rivera`/
  `acme.example.com`) на реальные из `org/`+`ai-clone/`. **Если язык фаундера не русский — переведи
  `prompt.md`/`rules.md` копии: язык промпта определяет язык вывода агента.** Для `example-noop`
  подставлять нечего — он уже `enabled:true`, просто скопируй.
- Проверь, что папка парсится:
  `pnpm exec tsx -e "import('./src/routines/agent-loader.js').then(m=>m.parseAgentFolder(process.cwd()+'/agents/<id>').then(r=>console.log('OK',r.id)))"`

### 9. Smoke-run + расписание
- Запусти агента один раз вручную: `pnpm dev:run <id>` (для первого smoke — `pnpm dev:run
  example-noop`). Команда сама откажется запускать disabled/неизвестного агента с понятной
  ошибкой. Убедись, что приходит ответ (запись в журнал, либо Telegram-пинг у агентов с
  `output: telegram`). Это и есть реальная проверка транспорта (момент активации).
- Если у агента cron-`schedule` — предложи установить launchd-плист (`pnpm install:launchd:routines`).

### Финал
Напечатай чеклист «готово / осталось»: что настроено, какой агент включён, как добавить
следующего (`/scaffold-agent <id>`), где читать (SETUP.md, docs/AGENTS.md, docs/UPDATING.md).
Затем `pnpm build && pnpm test` как финальная проверка зелёного состояния.
